\begin{frame}{Finance: Stakes and Accountability}
\begin{itemize}
\item \textbf{Consequential actions}: errors can affect customers, capital and institutional obligations, and some actions are difficult to reverse.
\begin{itemize}
\item Evidence supporting a conclusion does not itself authorize action.
\end{itemize}
\item \textbf{Dated information}: a financial result depends on what was available at the decision time and what version produced it.
\begin{itemize}
\item Reconstruct the recorded run, recompute frozen calculations and keep fresh model evaluations separate.
\end{itemize}
\item \textbf{Bounded authority}: the system must show who can act, within which mandate and limits, and who can stop it.
\begin{itemize}
\item Research acceptance, version approval and capital use are separate decisions.
\end{itemize}
\item \textbf{Continuity and governed change}: recover verified work after interruption and evaluate changes without losing the previous controls or version.
\end{itemize}
\end{frame}

\begin{frame}[t,shrink=15]{Why Separate Roles?}
\begin{itemize}
\item \textbf{Producer self-certification}: the Critic examines evidence in a separate context, but shared mistakes remain possible.
\item \textbf{Review changes the goal}: keep the mandate and acceptance criteria fixed.
\item \textbf{Control ownership}: the Orchestrator routes; code validates transitions.
\end{itemize}
\end{frame}

\begin{frame}{Contracts and Boundaries}
\begin{center}\resizebox{.70\textwidth}{!}{\input{figures/untrusted_document}}\end{center}
\begin{itemize}
\item \textbf{Task and artifact contract}
\begin{itemize}
\item Specify task, fixed inputs, permissions, return format and completion/failure conditions.
\item Link every artifact to its request and supporting evidence.
\end{itemize}
\item \textbf{Permission boundary}
\begin{itemize}
\item Retrieved filings and web pages are data, not authority.
\item A paid-data request still needs purpose, supplier, amount, expiry, identity and approver checks.
\item The classroom QT has no payment or broker access.
\end{itemize}
\end{itemize}
\end{frame}

\begin{frame}{Hooks and State Controller}
\begin{center}\resizebox{.82\textwidth}{!}{\input{figures/hook_concept}}\end{center}
\begin{itemize}
\item \textbf{Hook}
\begin{itemize}
\item Runs a callback when a host event occurs; records event metadata.
\item May block only when the host supports event blocking.
\end{itemize}
\item \textbf{State controller}
\begin{itemize}
\item Validates submitted artifacts, hashes, findings and numerical gates.
\item Decides whether the run advances, retries, waits or stops.
\end{itemize}
\item A hook observes an event; the controller governs workflow state.
\end{itemize}
\end{frame}

\begin{frame}{State and Checkpoints}
\begin{center}\resizebox{.82\textwidth}{!}{\input{figures/interruption_states}}\end{center}
\begin{enumerate}
\item Identity: case, request, candidate and prompt/version IDs.
\item Progress: pending role, round, retry count and deadline.
\item Evidence: paths and hashes that detect altered artifacts.
\item Findings: open problems and verified repairs.
\end{enumerate} \bigskip

Save verified state at each transition; a conversation's last line does not show which steps finished.
\end{frame}
